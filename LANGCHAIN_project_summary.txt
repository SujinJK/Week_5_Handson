What this project is, in plain words
Last week, we built a small AI assistant completely by hand -- every piece of logic
for "figure out what to do, do it, check your own work" was written in plain Python,
talking directly to Claude's API. This week, we rebuilt that exact same assistant, but
this time using LangChain -- a popular toolkit that provides ready-made building
blocks for exactly these kinds of AI assistants. The goal wasn't to make it do
anything new -- it's the same assistant, answering the same kinds of questions about
a made-up company's policies -- the goal was to see how much of last week's hand-written
code a toolkit can do for us instead, and what we give up by letting it.

What the assistant actually does (unchanged from last week)
Ask it a question and it will:
1. Think first -- sketch a short plan of what it thinks it'll need before doing anything.
2. Act -- use whichever tools its plan called for: a calculator, a search tool that looks
   through the company's internal documents, or a web search for anything not in those
   documents.
3. Double-check itself -- before showing you the answer, a second "reviewer" pass checks
   whether the answer is actually correct and properly backed up by what was found, and
   can send it back to be redone if something's wrong.

What actually changed this week
- Talking to Claude: last week we called Claude's API directly and had to manually read
  its raw response to figure out what it wanted to do next. This week, LangChain gives
  us a "chat model" object that handles that talking-to-the-AI part for us.
- Giving it tools: last week we had to write out, by hand, a technical description of
  each tool (what it's called, what information it needs) in a very particular format.
  This week, we just write a normal Python function with a helpful comment describing
  what it does, and LangChain automatically turns that into the technical description
  Claude needs. Much less typing, much less room for mistakes.
- Getting a clean verdict from the reviewer: last week, getting the reviewer to give us
  a clean "approved" or "needs fixing, here's why" required us to manually pick apart a
  block of text and hope it was formatted the way we expected. This week, we just tell
  LangChain "I want the answer in exactly this shape" and it hands back a properly
  structured, guaranteed-correct answer every time -- no more hoping.
- The web search tool: last week's web search ran entirely on Anthropic's own servers,
  which caused several tricky, hard-to-predict bugs (explained in last week's summary).
  This week we swapped it for a much simpler web search tool that runs like any other
  tool, which got rid of that entire category of headaches -- though it's worth knowing
  this was a deliberate choice we made, not something LangChain forced on us, and it
  means the two projects' web searches don't necessarily find the same things.

Where things came from
- The actual "search the company's documents" logic (turning documents into searchable
  chunks, finding the best matches, double-checking those matches with a second pass) is
  completely unchanged from Week 3 -- we didn't touch how the search itself works, only
  how the assistant is allowed to call it.
- The four-step thinking pattern (plan, act, reflect, and having a separate "reviewer"
  role) is unchanged from Week 4 -- we didn't redesign how the assistant thinks, only
  rewrote the plumbing underneath it.

Real bugs we hit while building this (not hypothetical)
- The new web search tool failed to even start up, because the search library behind it
  had recently been renamed by its developers, and our setup instructions still listed
  the old name. Nothing was wrong with our code -- it just needed the updated name.
- The assistant failed the first time we actually tried asking it a question, with an
  error saying the API key wasn't valid. We proved this had nothing to do with anything
  we built (by testing the exact same key directly against Claude's service and getting
  the same failure) -- the key itself had simply stopped working and needed to be
  replaced with a fresh one.

How much code actually got saved
Counting only the real lines of working logic (not comments, not blank lines), the
rewritten version needed about 30% less code than the hand-written one. Some of that
saving is genuinely thanks to the toolkit doing work for us automatically. But some of
it is because we also swapped out the complicated web search for a simpler one at the
same time -- so it wouldn't be fair to say "the toolkit alone cuts your code by a
third." Both changes together did.

What this does and doesn't prove
This shows, concretely, that a toolkit like LangChain removes a real amount of tedious,
error-prone hand-writing -- especially around describing tools and getting reliable,
structured answers back. It does not mean the toolkit is simply "better" -- it hides
some of what's actually happening under the hood, and this project intentionally didn't
use some of the toolkit's more advanced, automated pieces (like fully automated
multi-step agents) specifically so it would stay easy to compare, step by step, against
what we built by hand last week.

A second, smaller project: a GitHub repo explainer
On top of rebuilding last week's assistant, we also built a second, separate mini
assistant to practice the same two skills (giving an AI tools, and getting a reliably
structured answer back) in a completely different setting. You give it any public
GitHub project (like "psf/requests"), and it decides for itself -- by actually looking
at what it finds -- which of five things it needs to check: the project's basic info
(stars, language, license), its README, its file layout, a specific file, or its recent
commit history. It then hands back a clean, structured summary: what the project is,
which files matter most, whether it looks actively maintained, and whether it's
beginner-friendly.

The interesting part is that it doesn't follow one fixed checklist. We tested it on two
very different real projects and watched it make different choices each time. For
GitHub's own tiny joke "Hello World" demo repo, it checked the basic info, the README,
and the file layout -- and correctly figured out that its thousands of stars and forks
don't mean it's a real, actively-developed project, just a very popular practice
target. For a large, genuinely important project (the "requests" Python library), it
skipped looking at the file layout entirely, because the README already explained
everything clearly -- but it did check the recent commit history, and correctly noticed
that recent activity was mostly routine automatic updates rather than new features,
which it correctly read as a sign of a mature, stable project rather than one nobody's
maintaining anymore. That's real evidence the AI was actually deciding what to check
based on what it found, not just running through a script.

We also gave both of these mini assistants a nicer way to show their results: instead
of just plain text in a terminal, they now also produce a proper little webpage report
-- clear headline, color-coded status badges, and a clean summary -- that opens in any
browser. Building this actually caught a real, if minor, problem: the first version
let the AI describe the repo's programming language however it wanted, and for one
documentation-only project, it wrote a full sentence there instead of a short word --
which looked fine as plain text but broke the visual layout once we could actually see
it rendered. We fixed it by explicitly telling the AI "keep this one short," and it did.
That's a nice example of a mistake you literally cannot see until you look at something
visually instead of just as raw text.

A third, smaller project: a trip budget planner
The third and final mini assistant handles a very common real-world combination: mixing
"soft," researched information with "hard," exact numbers. You describe a trip in plain
language -- "Tokyo for 5 days with a $1500 budget" -- and it has to (1) search the web
for realistic price ranges for flights, hotels, food, and transport, since it can't know
those from memory, and (2) do the actual arithmetic to split that budget across
categories and check the numbers genuinely add up, since guessing at math is exactly
the kind of mistake an AI shouldn't be trusted to do in its head.

One deliberate safety choice here: the original idea was to give the AI a full Python
"REPL" -- basically letting it run any code it wants -- to do the math. We chose not to.
Since this assistant also reads real search results from the open internet, and those
results are not something we control or trust, letting the AI run arbitrary code based
on what it read online is a genuine risk, not just an abstract worry -- a malicious
webpage could try to trick the AI into running harmful commands on your own computer.
Instead, we gave it the same kind of restricted, "numbers and basic arithmetic only"
calculator used since week 4, which is more than capable of splitting a budget, but is
structurally incapable of doing anything beyond plain arithmetic.

We also hit a real, slightly funny mistake while testing this live: our very first test
run of "a $1500 budget" silently turned into "a 500 budget," because of how the command
line itself interpreted the dollar sign -- nothing to do with our actual code. The AI
handled the (accidentally wrong) $500 version very sensibly anyway, correctly explaining
that flights alone would blow that budget and suggesting sensible alternatives -- which
was itself a good reminder that "the AI gave a smart-sounding answer" and "the AI
answered the question you actually meant to ask" are two different things worth
separately checking. Once we fixed how we typed the command, it correctly planned a
real $1500, 5-day Tokyo trip: researching realistic prices, computing a full breakdown
that used about 81% of the budget, and correctly judging the trip as comfortably
affordable with some money to spare.

A few small but real improvements after testing
After trying these out, we made two more upgrades:

- The GitHub repo explainer now also reports who owns the project, when it was
  originally created, and its single most recent commit -- not just whether it
  "looks" active. Interestingly, once we required it to always check the actual
  commit history, it corrected its own earlier verdict: it had first called GitHub's
  joke demo repo "active," based only on the fact that lots of people still poke at
  it; once forced to check real commits, it correctly changed that to "unmaintained,"
  since nobody has actually committed real content to it since 2012. Requiring a bit
  more information changed the AI's actual judgment, not just what it reported.
- The trip planner now also explicitly captures where you're traveling from, not
  just where you're going. If you don't say where you're departing from, it no
  longer quietly assumes a city and presents that guess as fact -- it clearly marks
  the field as "not specified," while still using a reasonable, clearly-labeled
  assumption to actually look up flight prices.

We also caught one more real, easy-to-miss bug while testing these changes: three
separate small test suites (one per mini assistant) each passed perfectly fine on
their own, but broke the moment we ran all three together for the first time --
because two of them happened to have identically-named test files, and Python's
default test-discovery got confused about which file was which. Nothing was wrong
with the actual logic in any of them; it was purely a "how are these files organized
and identified" problem, fixed with one configuration setting. A good example of how
"each piece works on its own" and "all the pieces work correctly together" are two
different things worth checking separately.
